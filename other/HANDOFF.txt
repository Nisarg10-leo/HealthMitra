3. CONTENT TO PUT IN THE REPORT (ready to paste/adapt)
---------------------------------------------------------------------

DESIGN PRINCIPLES (quote these files as snippets):
 * Abstraction
   - data/repository.js: async methods hide storage; memoryStore is private.
   - notifications/channels.js: {name, deliver()} interface hides delivery.
   - api/client.js + api/index.js: components call medicationsApi.create(),
     never fetch/URLs; session header handled in one place.
   - hooks/useSpeech.js wraps Web Speech API -> features only see transcripts.
 * Modularity
   - one router per resource, one service per domain concept, one folder per
     feature on the client; registries (workspace/screens.js, ModalHost.jsx)
     mean adding a screen/dialog = 1 file + 1 line.
 * High cohesion
   - accessService.js is the single place for "who may see/edit a patient";
     doseService.js owns dose lifecycle; symptomService.js only knows the
     curated list; DoseCard.jsx is purely presentational.
 * Low coupling
   - dependency direction: routes -> services -> repository (never reversed);
     services do not import express; scheduler only calls services.
   - client features depend on WorkspaceContext/useSession, not on each other
     or on parent props; Workspace never imports a feature directly (registries).
   - errors: services throw HttpError; a single errorHandler middleware maps to
     JSON, so routes have no try/catch.
 * Separation of concerns: config.js (env), lib/ (pure helpers), middleware/
   (HTTP cross-cutting), services/ (rules), data/ (storage).

KEY DESIGN DECISIONS & WHY (pick 5):
 1. Layered client-server with server-side cron scheduler - reminders/missed
    detection must not depend on an elderly user's browser being open.
 2. Async repository over an in-memory store - lets the 10-day prototype run
    with zero setup while keeping the exact seam for PostgreSQL (schema already
    in server/sql/schema.sql); no service changes when swapping.
 3. Notification "channels" fan-out - alerts are recorded durably in-app and
    delivered through pluggable channels; FCM/SMS added later without touching
    business logic; every caregiver linked to a patient gets each alert.
 4. Permission model centralised in accessService (owner / edit / view) -
    one place to audit; every route calls assertCanView/assertCanEdit.
 5. Client feature folders + WorkspaceContext + registries - removed 10-prop
    drilling, each screen is independently understandable; CSS classes
    unchanged so redesign risk was zero (verified by 16 browser checks).
 6. Rule-based, curated symptom checker (static lookup, mandatory disclaimer,
    severe flag always escalates) - safety over cleverness.

MAINTAINABILITY / FUTURE CHANGES (how each is done now):
 - Postgres: implement data/repository.js methods with pg; nothing else moves.
 - Real auth (JWT): change middleware/requireUser.js + api/client.js header.
 - Push/SMS: add a channel object to notifications/channels.js.
 - Groq Whisper: add transcription before detectIntent in voiceIntentService.
 - New screen: features/<name>/Page.jsx + 1 line in workspace/screens.js +
   navigation.js. New dialog: 1 line in ModalHost.jsx.
 - Tests: services are plain async functions -> unit-testable without HTTP;
   e2e script already exists in work/tooling/e2e.js.
